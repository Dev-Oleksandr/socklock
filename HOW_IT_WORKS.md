# Як це працює

Простий опис кожного модуля і того, як дані проходять через програму. Мета — щоб кожну частину коду можна було пояснити на захисті.

## 1. Загальна картина

```
 сценарій (.md/.json) ──► script.py ──► generator.py ──► backends.py ──► Claude (cli / api) або mock
                           (розбір)      (промпт)           │
 library/ ──► library.py ──────────────────┘                ▼
 (стайлгайд + переможці)                   JSON з новими текстами
                                                            │
                     generator.py: копія сценарію, де замінено лише обрані елементи + ID
                                                            │
                           ┌────────────────────────────────┴───────────────┐
                           ▼                                                ▼
                 storage.py → data/socklock.db                    out/<ID>.md і .json
                           ▲
 accept / log-time ────────┤
                           │
 CSV з Meta ──► results.py ┤──► метрики CTR/CR/CPA/ROMI ──► переможці ──► library/winners/  (петля)
                           │
                 report.py ◄┘──► PASS / FAIL по метриках перевірки гіпотези
```

Вебсторінка (`web.py`) і командний рядок (`cli.py`) — це лише два «входи» в одну й ту саму функцію `generator.generate()`.

## 3. Модулі по черзі

### config.py — налаштування
Шляхи до папок, модель за замовчуванням (`claude-sonnet-5-5`), effort (`medium`), бізнес-числа (LTV $68, 240 модифікацій, 180 хв) і пороги перевірки гіпотези (50%, 120 хв, 130%). Функція `resolve_backend()` вирішує, який backend використати: mock — **тільки** якщо його явно попросили (`--mock` або `SOCKLOCK_MOCK=1`), інакше `--backend` або типовий `cli`.

### script.py — сценарій
Сценарій усередині програми — звичайний словник:
`{"title": ..., "scenes": [{"visual": ..., "voiceover": ..., "onscreen_text": ...}]}`.
- `parse_markdown()` йде рядок за рядком: `#` — назва, `##` — нова сцена, `Ключ: значення` — поле сцени. Різні написання ключів (VO, Voiceover, Line, On-screen, OST...) зводяться до трьох полів через словник `FIELD_ALIASES`. Рядок без ключа продовжує попереднє поле.
- `parse_json()` робить те саме для JSON.
- `current_elements()` повертає поточні тексти трьох елементів: hook = озвучка сцени 1, first_lines = озвучка сцен 2–3, onscreen_text = текст на екрані всіх сцен.
- `apply_rewrite()` — ключова функція: робить **копію** сценарію і замінює в ній лише обрані елементи. Так структура сценарію гарантовано лишається тією самою, а візуал і решта тексту не змінюються, навіть якщо модель щось зайве поверне.
- `to_markdown()` пише сценарій назад у той самий Markdown-формат, який читає парсер.
- **Front matter.** `split_front_matter()` відрізає необов'язковий блок `---` … `---` на початку файлу і читає з нього рядки `ключ: значення` (ділимо лише по першій `:`, тож `context: Продукт: ...` працює). Дозволені ключі — `context`, `elements`, `variants`, `model`, решта ігнорується. Для JSON ті самі ключі беруться з верхнього рівня. `clean_settings()` перевіряє значення: невідомі елементи й нечислову кількість відкидає, тоді лишаються типові. `load_document()` повертає пару (сценарій, налаштування); `load_script()` — лише сценарій.

### ids.py — ID варіантів
- `new_generation_id()` → `SLM-<рррр><мм><дд>-<4 символи>`; символи без 0/O/1/I, щоб їх не плутали при ручному введенні. Унікальність перевіряється по базі (`generator.new_unique_generation_id`).
- `variant_id()` додає `-v<n>`.
- `find_variant_id()` шукає ID будь-де в назві оголошення регулярним виразом `SLM-(\d{8})-([A-Za-z0-9]{4})-v(\d+)`. «Огорожі» `(?<![A-Za-z0-9])` і `(?![0-9])` не дають знайти ID всередині іншого слова. Регістр нормалізується. Немає ID → це контрольне оголошення.

### library.py — бібліотека стилю
`build_library_text()` склеює `style_guide.md` і всі файли з `winners/` в один текст з тегами `<style_guide>` і `<winning_scripts>`. Файли сортуються за назвою, щоб текст був **байт-у-байт однаковим** при кожному запуску — це потрібно для кешування промпту. `add_winner_file()` (команда `library add`) спершу перевіряє, що файл — коректний сценарій, потім копіює. `save_winner_script()` записує переможця з бази в `winners/<ID>.md` разом із рядком `Result: CTR ..., ROMI ...`, щоб модель бачила, чому це переможець.

### backends.py — розмова з моделлю
Три функції з однаковим результатом `(data, served_model, usage)`:

- **`call_cli()`** (типовий) запускає `claude -p` через `subprocess.run`:
  - `--output-format json` — відповідь приходить як JSON-«конверт»;
  - `--json-schema` — структурований вивід за нашою схемою `VARIANTS_SCHEMA`;
  - `--system-prompt` — наш стабільний префікс замість системного промпту Claude Code;
  - `--model`, `--effort` — модель і глибина міркувань;
  - `--tools ""`, `--strict-mcp-config`, `--safe-mode` — **жодних інструментів**, MCP-серверів, особистих CLAUDE.md чи плагінів: модель лише пише текст, без доступу до файлів і терміналу;
  - `--no-session-persistence` — ці запуски не зберігаються як сесії.
  Повідомлення користувача (сценарій) передається через stdin, бо воно може бути довгим. Таймаут — 300 с. `parse_cli_output()` бере `structured_output` з конверта (або, якщо його немає, шукає JSON у тексті), перевіряє форму через `validate_variants()`. Якщо відповідь не вдалося розібрати — **одна повторна спроба**. Якщо `claude` не встановлений, не залогінений, відмовив або не встиг — зрозуміла помилка, нічого не зберігається.
- **`call_api()`** — офіційний SDK `anthropic` для майбутнього продакшн-бота з ключем: `client.beta.messages.create` зі структурованим виводом (`output_config.format`), явним `effort`, кешуванням системного блоку (`cache_control: ephemeral`) і server-side fallback (`fallbacks="default"`, бета `server-side-fallback-2026-07-01`: якщо класифікатор безпеки відмовить, API сам повторить запит на рекомендованій моделі). Перед читанням відповіді перевіряється `stop_reason` (`refusal`, `max_tokens`), блоки читаються за типом (відповідь може починатися з блоку thinking). Помилки SDK ловляться від конкретних до загальних (автентифікація → модель не знайдена → ліміт → інші статуси → мережа).
- **`mock_variants()`** — фейкові детерміновані тексти з шаблонів, позначені `[MOCK]`. Потрібні для тестів і демо без інтернету.

### generator.py — промпт і головна функція
`generate()` робить три кроки:
1. перевіряє запит (`check_request`) і отримує нові тексти від backend-у;
2. для кожної відповіді моделі робить повний сценарій через `apply_rewrite()` і дає йому ID `...-v1`, `...-v2`...;
3. зберігає генерацію в SQLite і пише `out/<ID>.md` та `.json`.
Тут же `build_system_prompt()` і `build_user_message()` — див. розділ 4. `--show-prompt` друкує обидва тексти без виклику моделі.

### storage.py — база SQLite
Чотири таблиці: `generations` (вхідний сценарій, модель, backend, елементи, контекст, токени), `variants` (ID, повний сценарій варіанта, `accepted_at`), `time_logs` (хвилини на модифікацію), `ad_results` (останній імпорт з Meta). `open_db()` — контекстний менеджер: відкриває файл, створює таблиці, якщо їх немає, робить commit і завжди закриває з'єднання. Запити — звичайний SQL з `?`-параметрами (без ORM і без ризику SQL-ін'єкцій).

### results.py — результати з Meta
- `normalize_header()` зводить назви колонок до простого вигляду: `Amount spent (USD)` → `amount spent`, `Clicks (all)` → `clicks`. Далі `COLUMN_ALIASES` для кожного поля перелічує можливі назви в порядку переваги (напр. `link clicks` важливіше за `clicks (all)`). Немає обов'язкової колонки → помилка зі списком того, що є.
- `read_meta_csv()` читає CSV (BOM, роздільник `,`/`;`/таб), пропускає підсумкові рядки без назви, сумує рядки з однаковою назвою оголошення (експорт по днях), визначає групу (є ID → група перевірки, у коді `pilot`; немає → контрольна група, `control`). Якщо немає колонки цінності конверсій — value = purchases × LTV $68, і це прапорець `value_estimated`, який програма показує.
- `add_metrics()` — CTR, CR, CPA, ROMI; `safe_div()` повертає «немає даних» замість ділення на нуль.
- `group_totals()` — суми по групах, метрики рахуються на сумах.
- `pick_winners()` — оголошення групи перевірки з ROMI ≥ порогу і CTR ≥ медіана CTR контролю × коефіцієнт (і spend ≥ мінімуму, якщо задано).
- `import_results()` — уся петля: прочитати → порахувати → вибрати переможців → зберегти в базу → скопіювати сценарії переможців у `library/winners/` (повторний імпорт не дублює).

### report.py — звіт перевірки гіпотези
`build_report()` бере з бази кількість згенерованих/прийнятих варіантів, хвилини та останній імпорт Meta і порівнює 4 метрики з порогами: PASS / FAIL / НЕМАЄ ДАНИХ. Додатково: прогноз потужності (240 × 180 хв ÷ середній час), acceptance окремо по кожній моделі (для A/B Sonnet vs Opus) і попередження, якщо в базі є mock-генерації.

### web.py — вебсторінка
Стандартний `http.server` (`ThreadingHTTPServer`: кожен запит у своєму потоці, тож «простоюче» з'єднання браузера чи 15-секундна генерація не блокують інші запити; SQLite безпечний, бо `storage.open_db()` відкриває окреме з'єднання на кожен виклик). CSS і JavaScript — звичайні рядки `STYLE` і `SCRIPT` у файлі; HTML навколо них збирають f-рядки, і весь текст від користувача чи моделі проходить через `html.escape()`. Сервер слухає лише `127.0.0.1`.
- **Мінімальний дизайн:** темна тема; на широкому екрані (від ~1000 px) дві колонки до 1280 px: форма зліва (~40%, закріплена вгорі під час прокручування), результати справа (~60%, до першої генерації порожньо, під час генерації — тихий спінер); на вузькому — одна колонка, результати під формою; шрифт Nunito (без інтернету — системний). На екрані лише поле сценарію, кнопка «Згенерувати» і результати. Акцентний колір #93c47d — тільки на головній кнопці й рамці фокусу, решта — нейтральні сірі.
- **Другорядне — компактне:** над полем дві маленькі кнопки «Приклади» і «Імпортувати сценарій»; кількість, елементи, модель і контекст сховані в згорнутому блоці «Налаштування» з одним рядком-підсумком (напр. «Хук, перші фрази, текст на екрані · 10 варіантів · Sonnet 5.5»). Пояснювальних текстів немає: модель видно в підсумку «Налаштування»; у mock-режимі біля назви є бейдж MOCK.
- **Імпорт і приклади працюють у браузері:** JavaScript читає файл (`file.text()`; можна й перетягнути на поле), відрізає front matter за тими самими правилами, що й `split_front_matter()` у Python, заповнює всі поля і пише під полем коротку примітку «назва · N сцен». Шість прикладів вбудовано в сторінку як JSON (`<script type="application/json">`).
- `POST /generate` викликає той самий `generator.generate()`, що й CLI. Кожен варіант — ID сірим моноширинним шрифтом, маленька іконка копіювання і рядки сцен простим текстом (мітки VO / On-screen сірі; новий текст злегка підсвічено — ледь помітний зелений фон і тонка ліва смужка; текст, який модель не змінила, сірий без підсвітки). Над списком — «Копіювати все». Модель береться лише зі списку дозволених (`MODEL_OPTIONS`).
- Поки модель працює, кнопка вимикається і показує спінер «Генеруємо…». Помилки показуються простою карткою з підказкою (для `cli` — `claude auth status`).

### demo.py — демо-дані
Копіює файли з `socklock/demo_data/` у `library/` і `samples/`, створює одну mock-генерацію «минулого тижня», позначає 6 її варіантів прийнятими, записує 110 хв і пише синтетичний `meta_export.csv`: 6 оголошень групи перевірки з цими ID і 6 контрольних. Числа підібрані так, щоб було видно, як працюють пороги: 3 переможці, 1 програє за CTR, 1 за ROMI, 1 за обома.

### cli.py і \_\_main\_\_.py
`build_parser()` описує команди через `argparse`; кожна команда — маленька функція `cmd_...`, яка викликає потрібний модуль і друкує результат. Для `generate` функція `generate_options()` поєднує налаштування за пріоритетом: явний прапорець → front matter файлу → типове значення (тому в прапорців `-n`, `--model`, `--context` типове значення `None`). Помилки (`ValueError`, `GenerationError`, файл не знайдено) друкуються зрозумілим повідомленням і код виходу 1. `__main__.py` дозволяє писати `python -m socklock`.

## 4. Що саме йде в модель і чому

Подивитися повний промпт: `python -m socklock generate samples/winning_script.md --show-prompt`.

**System (стабільний префікс, однаковий при кожному запуску):**
1. `SYSTEM_INSTRUCTIONS` — роль (копірайтер direct-response для SockLock, ринок США, Meta Reels), завдання (переписати лише обрані елементи, футаж не змінюється), визначення трьох елементів і правила: дотримуватися стайлгайду, вчитися на переможцях без копіювання, текст має пасувати до візуалу сцени, **не вигадувати** обіцянок, цін і знижок, варіанти мають відрізнятися кутом подачі.
2. `<style_guide>` — тон, факти про оффер (єдині дозволені твердження), заборонені слова й твердження (включно з правилом Meta про персональні атрибути), ліміти довжини.
3. `<winning_scripts>` — минулі переможці з їхніми результатами (few-shot приклади).

**User (змінна частина):** вихідний сценарій у JSON, контекст (вільний текст `Context: ...` з форми, front matter або `--context`, а також `--product` / `--audience` / `--angle`; лише заповнені поля), і точне завдання: «Write N variants. Rewrite ONLY: ...», скільки рядків потрібно для кожного елемента, «для необраних елементів поверни порожній рядок або порожній список», назви кут кожного варіанта.

**Чому саме так:**
- **Стабільне — спочатку, змінне — потім.** Кешування промпту працює як збіг префікса: якщо початок запиту байт-у-байт той самий, він береться з кешу (дешевше і швидше). Тому в system немає дат чи ID, файли бібліотеки відсортовані, а сценарій і N — у повідомленні користувача. На backend-і `cli` Claude Code сам ставить кеш на системний промпт (у пробному запуску записано ~4 тис. токенів у кеш); на backend-і `api` ми ставимо `cache_control` явно. Мінімум для кешу на Sonnet 5.5 — 512 токенів; наш префікс більший.
- **Структурований вивід (JSON-схема)** замість «поясни текстом»: відповідь одразу перевіряється і розбирається, без крихкого парсингу.
- **Схема одна й та сама для будь-якого вибору елементів.** Тому для необраних елементів модель повертає `""`/`[]`, а Python їх ігнорує. Змінна схема зламала б кеш.
- **Модель повертає лише нові тексти, а не весь сценарій.** Збирає сценарій Python (`apply_rewrite`): так структура гарантовано та сама, і змінюються лише обрані елементи.
- **Effort `medium`** — баланс якості й швидкості для коротких рекламних текстів; змінюється прапорцем `--effort`.
- **Без інструментів** у `claude -p`: генерація тексту не потребує доступу до файлів чи терміналу, тож ми його не даємо.

## 5. Петля зворотного зв'язку

`generate` → дизайнер вставляє ID у назву оголошення → Meta крутить рекламу → `import-results` знаходить ID у назвах, рахує метрики → переможці копіюються в `library/winners/` → при наступному `generate` вони вже в промпті як приклади. Так інструмент поступово «вчиться» на тому, що реально працює в рекламі SockLock.

## 7. Можливі питання на захисті

- *Чому CLI, а не API?* У студента немає API-ключа; Claude Code CLI працює на підписці. Для командного бота є готовий `api`-backend.
- *Що, якщо модель поверне менше варіантів чи рядків?* Зайві варіанти відкидаються, яких бракує — програма попереджає; для відсутніх рядків лишається оригінальний текст.
- *Як не сплутати групу перевірки й контрольну групу?* Лише за ID у назві оголошення: є ID — група перевірки, немає — контрольна група.
- *Чому ROMI = value ÷ spend?* Так визначено в брифі; поріг 130% означає, що цінність (або purchases × LTV) перевищує витрати на 30%.
- *Чи може mock потрапити в результати непомітно?* Ні: він вмикається лише явно, у базі позначений `backend = mock`, у виводі є банер, а `report` попереджає про mock-генерації.
